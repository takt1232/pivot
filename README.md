# Pivot

One codebase, two platforms: a local-first project and task app built with Next.js and Expo/React Native, sharing screens, routing and a design system.

Projects hold tasks; tasks carry subtasks, comments and a derived progress percentage when subtasks exist. Everything is stored on the device. There is no backend, account or sample data; the app opens on an empty project list and the owner creates the first project.

## Stack

| Layer             | Version   | Notes                                                                |
| ----------------- | --------- | -------------------------------------------------------------------- |
| Next.js           | `16.4.5`  | App Router, Turbopack                                                |
| React / React DOM | `19.1.0`  | Single copy, enforced with root `overrides`                          |
| Expo SDK          | `54.0.38` | React Native `0.81.5`                                                |
| Expo Router       | `6.0.24`  | File-based native routes                                             |
| Solito            | `5.0.0`   | Cross-platform `Link` and `useRouter`                                |
| NativeWind        | `4.2.7`   | Tailwind CSS `3.4.19` (NativeWind 4 does **not** support Tailwind 4) |
| react-native-web  | `0.21.4`  | Web renderer for the shared components                               |
| Turborepo         | `2.x`     | Task runner                                                          |

Expo SDK 54 is the last version covered by Solito's tested compatibility matrix. That is a deliberate choice, not an accident. See [Upgrades](#upgrades).


## Get started

```sh
npm install
npm run web       # http://localhost:3000
npm run native    # Expo dev server
```

`npm run native` works with Expo Go on SDK 54. To build a native client instead:

```sh
npm run android   # needs Android SDK / emulator or a device
npm run ios       # macOS only, or use EAS
```

Other commands:

```sh
npm run typecheck        # tsc in all three workspaces
npm run build            # production Next.js build
npm run format           # Prettier + Tailwind class sorting
```

## Build an Android APK

`apps/expo/android/` is generated by `expo prebuild` and gitignored, so `app.json` stays the source of truth.

### Prerequisites

- JDK 17, with `JAVA_HOME` set.
- Android SDK with `platforms;android-36`, `build-tools;36.0.0`, `ndk;27.1.12297006` and `cmake;3.22.1`. Expo SDK 54 pins NDK 27.1, and Reanimated 4 plus the New Architecture compile C++, so neither is optional:

  ```sh
  sdkmanager --install "ndk;27.1.12297006" "cmake;3.22.1"
  ```

- `adb`, plus a device with USB or wireless debugging enabled (`adb devices` should list it).

### Build

```sh
cd apps/expo
npx expo prebuild --platform android   # once, and again after app.json changes
cd android
.\gradlew.bat assembleRelease -PreactNativeArchitectures=arm64-v8a
```

Use `./gradlew` on macOS/Linux. The APK lands at `apps/expo/android/app/build/outputs/apk/release/app-release.apk` (~27 MB for arm64).

`-PreactNativeArchitectures=arm64-v8a` builds only the ABI current phones use. Drop it for a universal APK that also covers x86_64 emulators and 32-bit devices; that takes longer and produces a larger file.

### Install

```sh
adb install -r app/build/outputs/apk/release/app-release.apk
adb shell am start -n com.pivot.app/.MainActivity
```

`npm run android` is the debug path: it generates `android/` if needed, builds, installs, and expects Metro to be reachable. Use `assembleRelease` when you want a self-contained APK that runs without a dev server.

### Notes

- The release variant is signed with the debug keystore that `expo prebuild` generates. Good enough to install and test, not to publish.
- `app.json` has no `icon` or `splash` yet, so the launcher shows the default Expo icon.
- `apps/expo/metro.config.js` sets `EXPO_NO_METRO_WORKSPACE_ROOT=1`. Expo otherwise makes the monorepo root Metro's server root, while the React Native Gradle plugin passes entry paths relative to `apps/expo`; release builds then fail with `Unable to resolve module ./../../node_modules/expo-router/entry.js`.
- On low-memory machines (8 GB or less), shrink the Gradle heap in the generated `apps/expo/android/gradle.properties` or the Kotlin daemon and `clang` will run out of memory:

  ```properties
  org.gradle.jvmargs=-Xmx1536m -XX:MaxMetaspaceSize=512m -XX:ReservedCodeCacheSize=192m
  org.gradle.parallel=false
  org.gradle.workers.max=1
  kotlin.compiler.execution.strategy=in-process
  ```

  Then build with `--no-daemon --max-workers=1`. The file is gitignored, so reapply these values after regenerating `android/`.

## How the shared code works

- `packages/app` is the only place product UI should live. Both apps import from `@pivot/app`.
- Route files in `apps/next/app` and `apps/expo/app` are deliberately thin adapters. They read the `id` param from their platform router and pass it to the shared screen. This keeps Solito responsible for navigation, not for param plumbing.
- `solito/link` and `solito/navigation` are used inside shared screens. On web they delegate to `next/link` and `next/navigation`; on native they delegate to Expo Router / React Navigation.
- Styling is NativeWind `className` everywhere. Theme colors are static class strings in `packages/app/provider/theme.tsx` (light/dark), not dynamically generated names, so Tailwind can see them.
- `SafeAreaProvider` receives zeroed initial metrics on web. Without metrics it renders nothing during SSR, which would produce an empty first paint.
- Shared buttons go through `packages/app/components/pressable.tsx`. On web it behaves like a normal `Pressable` (`onPress`, so keyboard activation works). On native it fires on `onPressIn`, working around a React Native 0.81 + New Architecture + native-stack bug that drops `onPress` on some Android devices.

### Local data

Projects and tasks live in one versioned payload under `pivot.store.v1`. The store hydrates once on mount and will not write before it has read, so an existing sheet is never overwritten by the first empty render.

- `packages/app/data/storage.ts` is used on web and reads `localStorage`.
- `packages/app/data/storage.native.ts` is picked by Metro on iOS/Android and uses `@react-native-async-storage/async-storage`.
- Both implement `StorageAdapter` from `storage-types.ts`, so the backing store can be swapped for SQLite or Supabase without touching feature code.

There is no sample data: the app opens on an empty project list and the owner creates the first project.

### NativeWind and the Next.js App Router

NativeWind does not support React Server Components. Every Next.js route that renders shared components starts with `'use client'`. The root `layout.tsx` is a server component and uses the documented escape hatch:

```tsx
/** @jsxImportSource react */
```

Do not remove that pragma. Without it the layout tries to use NativeWind's JSX runtime on the server.

`apps/expo/tailwind.config.js` only re-exports the root config. NativeWind starts its Tailwind CLI in the app directory and does not forward `configPath`, so without that file Tailwind finds no config and emits zero utilities. The app still renders, but every `className` is ignored.

## Dependency rules

| Kind of dependency             | Install in                              |
| ------------------------------ | --------------------------------------- |
| Pure JS used by shared screens | `packages/app`                          |
| Native modules / Expo packages | `apps/expo` (prefer `npx expo install`) |
| Web-only packages              | `apps/next`                             |
| Tooling used by the whole repo | root `devDependencies`                  |

`@react-native-async-storage/async-storage` is declared in both `apps/expo` (so Expo autolinks it) and `packages/app` (because `storage.native.ts` imports it).

Also:

- **Never add `react` to `apps/expo`.** React lives in `apps/next`; Expo must consume the hoisted copy. `npm ls react` should show exactly one version.
- Install native packages with matching versions in any other workspace that imports them. Version drift is the classic monorepo failure mode.
- `semver` is listed directly in `apps/expo` because Metro's monorepo resolver (`disableHierarchicalLookup`) cannot reach the nested copy under `react-native-reanimated`. It is a build-time requirement, not a UI dependency.

## Upgrades

The real upgrade unit is the **Expo SDK**, because it pins React, React Native and react-native-web together.

- Next.js can move within `16.x` independently. The `next/link` and `next/navigation` APIs Solito uses are stable.
- Do not bump React on its own. Move it with an Expo SDK upgrade.
- NativeWind v4 is pinned to Tailwind 3. Do not install Tailwind 4 until you migrate NativeWind v5.
- After an Expo upgrade, re-test Solito's native `Link`/`useRouter` path. That is where React Navigation changes can surface.

If Solito ever blocks a Next upgrade, the escape hatch is a platform-specific navigation module (`.web.ts` using `next/link` / `next/navigation`, `.native.ts` using Expo Router). The shared screens only need a router interface.
